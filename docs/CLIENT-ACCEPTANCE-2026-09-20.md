# 紧凑响应的真实客户端验收

## 任务与冻结边界

针对 OpenSession `543e874e697523bf474f494bcf897a17f19587de` 的两个真实审查问题，
比较同一 CodeFacts 二进制的 `full` 和 `compact`：协议缓存的 revision 失效条件，
以及主会话轮次排序与子会话隔离。两题都要求识别同名 Map/Set 调用候选的局限，
给出已有测试支持的修改或验证计划，并解释来源哈希和关系方向。

这是有指引的客户端理解/兼容性验收。提示明确要求先查询相关目标，并在存在
`next.callees` 时读取一页；它不评估自然使用率，也不比较不用工具或 CodeGraph。

- 固定源码清单：446 个文件，前后逐文件核验 SHA-256。
- 二进制 SHA-256：`66cae60808c437998a43eb9006908e9bdc62fa219feb404f88269caa77c1e5c7`。
- 客户端：Codex CLI `0.155.0-alpha.9.2`，完整桌面 runtime；`gpt-6-astra / ultra`。
- 两组使用相同提示、schema 描述和底层服务；本地透明代理只设置 `format` 默认值，
  保留全部实际响应。原生预检确认其余 schema 相同、响应未经投影。
- 顺序：缓存 full → 缓存 compact → 轮次 compact → 轮次 full；每组合一次，共四次。
- 每次新建外部 SQLite 状态，计入索引启动成本；操作系统缓存共用，没有声称冷盘对照。
- 每次最长 10 分钟；提示要求实际 MCP 和 shell 调用合计不超过 16，事后核查。
  时间上限由进程树强制终止，调用上限是合格门槛。
- 业务正确性按冻结的每题四项标准独立评分，评分者不看 token、时间及组别映射；
  答案中的分页描述可能透露格式，因此不称完全盲评。真实调用、续页、哈希/置信度和
  只读范围由主审另外检查。
- 不修改失败题的提示，不替换失败运行；实际环境失败则停止尚未派发的正式运行。

真实客户端预检已完成：2 次相关 MCP 查询、1 次源码读取，正确解释 `ping → helper`
及共享哈希，36.63 秒，69,259 total tokens（56,832 cached input；12,427 非缓存输入加输出）。
stdout 与原始 rollout 用量一致，没有策略拒绝。该成本单独统计，不混入正式对照。

本地可复查材料在 `target/client-acceptance-20260920/`：`freeze.json` 保存模型、提示、
顺序和文件哈希，`RUBRIC.md` 保存评分规则；`formal/`、代理 JSONL 和原始 rollout
保存调用及用量。原始材料留在忽略目录，避免把本地会话数据加入仓库。

## 结果

四次运行均完成，业务正确性各为 **4/4**；两次 compact 都使用了实际返回的游标，
并正确解释共享哈希、隐含锚点、方向及 static/heuristic 的区别。四次均未出现策略拒绝、
MCP 错误或超时，实际调用未超过 16；源码 446 个文件的哈希保持一致。

用量直接取客户端 `turn.completed`，与对应原始 rollout 累计值逐项一致。
total 为 input + output，已包含 cached input；非缓存输入单列，output 已包含报告的
reasoning output，避免重复计数。token 数不是字符串长度估算，也没有换算为金额。

缓存 full 首次打印整个 MCP 结果后被客户端截断，重查一次并手工筛选字段。
轮次 full 只打印 TextContent，仍被截断，30 条服务端 callee 中只有 27 条完整对象
能在模型可见输出中逐字核对，随后定点读取源码。两次 compact 都完成续页，
MCP 返回没有客户端截断。以上不包含各组普通源码读取的输出截断：缓存 compact、
轮次 compact、轮次 full 各出现一次，仍需计入整个工作流。缓存两组各有一次 shell
非零退出，保留了相关通配路径问题，不将其误记为 CodeFacts 服务失败。

客户端预检及缓存 compact 的 trace 还确认：Code Mode 中直接 `text(result)` 会把
`content` 和 `structuredContent` 一起打印；取其中一种表示可以避免重复注入。
其他调用实际选择了 `structuredContent` 或 TextContent，这也是 agent 行为的一部分。
MCP 协议的两种表示仍为客户端兼容而保留，不能由原始封装大小直接推算模型实际输入。

这组指导刻意要求验证续页：compact 的两题实际收到 43 / 48 条 callees，full 每次
最多 30 条。因此正式组并非同等事实数量的纯格式对照；固定问题相同，但分页、源码
读取、模型轮数与缓存命中均有差异。只有先前的原生等价核验控制了事实数量。
本轮 n=1/组合足以记录客户端是否能理解新格式，不足以把上述成本差异归因于格式本身。

正式四次累计 **867,935 total tokens、501.08 秒**；加一次 readiness 为
**937,194 total tokens、537.71 秒**。非缓存输入加输出分别为 222,687 / 235,114。
这些是被测模型运行成本；资料准备、工程实现、独立评分与主审的 token 尚未汇总，
不把它们当作零，也不据此计算产品投资回报。

## 决定与停止点

- 保留 compact 及 16 KiB 初始预算：本轮通过了理解/续页门槛，并消除了这两例 MCP
  输出截断。16 KiB 仍不是经过最优性验证的预算，不因单次 token 结果继续缩小。
- 不把“字节减少”改写成“agent token 节省”。项目当前的可证实价值是有来源的事实、
  有界输出和明确的不确定性；继续投入应围绕真实消费者遇到的失败。
- 发布时同步独立插件的版本/pin/技能；指导按任务需要续页，并在 Code Mode 中只选
  一种等价响应表示。兼容消费者仍可选 `format=full`。
- 本轮四次正式运行到此关闭，不追加提示变体或重跑以追求更好数字。后续使用自然任务
  观察重复读取、失败与总成本，再决定是否调整预算或关系排序。

客户端兼容性和三平台 CI 门槛已完成。发布仍需独立插件同步及安装后的实际加载验收；
本轮没有执行合并、打 tag 或 npm 发布。
